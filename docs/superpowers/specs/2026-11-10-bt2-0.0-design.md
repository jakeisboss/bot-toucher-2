# BT2 0.0 — Windows shell design

Status: proposed; implementation has not started.

## Intent and scope

Build an independent Windows-first WPF application in the existing BT2 repository. Version 0.0 owns only navigation, window/rail/workspace layout, basic shell state and built-in observation-only hardware monitoring. No separate large application-information panel.

No updater, widget host/runtime/messaging, packet loading, workload controls, execution, allocator, result schemas or research logic. Named future surfaces are navigation destinations, not working future systems.

## Approaches

WPF preserves useful Windows UI and telemetry code from BT1. Avalonia would allow Linux launch checks but would require view adaptation and platform-specific telemetry. The user selected Windows-first WPF on 2026-11-10. Do not change frameworks for cloud convenience.

## Reference inspection and reuse

BT1 main contains policy/direction documents rather than application source. Inspected application source at release-0.2.1.3-20261009, commit 6c30c11fe60a490ebeac2f81732988595eaaefc6. BT1 is reference material, not BT2 authority.

Reuse where practical: hardware snapshot records; Windows CPU/RAM/GPU/VRAM sampling implementation; dark shell resource colors; three-column rail/splitter arrangement; established navigation names and Packet Center hierarchy. Record exact provenance and adaptations in BT2 documentation.

Do not carry over the AppServices graph, StoragePaths dependency merely for a disk probe, Bridge integration, project checklist semantics, update actions, results widgets or workload-specific views. BT1's monitor panel depends on a card refresh provider; BT2 will own its monitor sampling lifetime directly, independently of any widgets.

## Project structure

- `src/BotToucher2.App`: WPF executable, shell window, resources, destination views, built-in monitor presentation and application startup/shutdown.
- `src/BotToucher2.Core`: only shell navigation/layout state and hardware snapshot/sampling services. No general plugin framework or speculative interfaces.
- `tests/BotToucher2.Core.Tests`: targeted navigation/state and telemetry boundary checks.
- Windows shell smoke checks: actual WPF window creation and interactions, run on a Windows host; keep assertions limited to meaningful 0.0 behavior.
- `docs`: reference/reuse decisions, startup instructions, verification results and 0.0 handoff.

Use .NET 8, matching inspected BT1, with version 0.0.0. App and core have independent BT2 names and no runtime reference to BT1. Final implementation may split small files by responsibility without adding projects beyond these needs.

## Physical shell and destinations

Window defaults approximately 1280×800 with a practical minimum size. Use BT1's dark palette and conventional WPF controls. A compact top area contains title/version and controls to restore either rail. The body has left navigation, flexible central workspace and right rail, with draggable splitters. Long rail content scrolls. No extra information dashboard surrounding the workspace.

Left navigation: Home, Packet Center, Data, Lab, Settings, Help/About. Home and Lab provide empty central workspace surfaces; no sample workload or fake live results. Packet Center contains Project, Packets and Activity tabs. Update Center is reached within Packets and has a return path; it contains only a deferred-functionality message. Settings and Help/About contain only actual shell settings/help and version information.

Right rail: Context and Widgets tabs. Context displays current shell destination without invented project/session state. Widgets is an empty future destination with no add/load/execute controls. Built-in hardware monitoring occupies a persistent section of this rail, outside the Widgets surface. Hiding the right rail hides its contents; the top restore control remains available.

Use keyboard-accessible controls, visible focus and accessible names. Preserve familiar BT1 navigation shortcuts where they remain meaningful. At minimum verify both rails can hide/restore, resize within bounds and leave central content usable at minimum window size.

## Ownership and state

One shell state owner validates selected destination, Packet Center section, rail visibility/widths and right-rail selection. Views consume that state; they do not become authorities for future systems. Persist only these layout preferences under a BT2-specific LocalApplicationData directory. Invalid or unreadable preferences fall back to defaults with a visible nonfatal notice; do not overwrite damaged data silently. No session/test schemas.

Workspace readiness means a clear central content boundary ready for later replacement, not an implemented universal widget host. Do not define widget contracts in 0.0.

## Hardware monitor

Reuse the BT1 snapshot shape and reliable Windows sampling code with minimal namespace/dependency changes. Sample serially on background work, approximately every two seconds. Never enumerate GPU counters on the dispatcher. UI receives completed immutable snapshots. Cancel sampling on close and dispose counter resources after in-flight work completes.

Show CPU, GPU, RAM and VRAM with units, timestamp and honest sampling/unavailable states. Do not fabricate zeros when telemetry is unsupported. Retain clean disk telemetry only if it adds no storage architecture dependency. Temperature remains unavailable unless an already reliable provider exists. The monitor exposes no allocation or resource-control settings.

## Failure behavior

Telemetry failure leaves the shell usable and shows unavailable/error status. Prevent overlapping polls and unobserved background exceptions. Preference failures are nonfatal. Placeholder surfaces contain no buttons implying unfinished functionality works.

## Validation and acceptance

Cross-build the WPF app with Windows targeting enabled, build core and run targeted portable tests in this Linux environment. Validate a clean checkout/build path and no dependencies on BT1 or unfinished systems.

Actual launch, navigation, both rails, splitters, resizing, hardware monitor rendering and responsiveness require Windows. Add reproducible Windows build/test/launch instructions and targeted automated smoke coverage where feasible. Cross-compilation is not launch evidence. If no Windows executor is available, explicitly mark those acceptance checks unverified and 0.0 incomplete rather than claim success.

Final handoff includes structure, reused/rejected BT1 pieces, significant files, actual verification evidence, each requested Definition of Done item PASS/FAIL, known limitations, 0.1 readiness and final branch/commit/working-tree status. Stop at 0.0.
